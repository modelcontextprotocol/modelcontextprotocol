Each CLI run connects to a server, invokes the single request you name with `--method`, prints the result, and exits. That makes it a good fit for CI pipelines, shell one-liners, and coding agents that need to verify a server change immediately.

```bash
npx @modelcontextprotocol/inspector --cli node build/index.js --method tools/list
```

<Tip>
  Running several commands against the same server, or a flow that spans one
  session (tasks, subscriptions, elicitation)? The [mcpdo connection
  client](/docs/draft/tools/inspector/mcpdo) connects once and keeps the
  connection open between commands.
</Tip>

The examples below use the installed `mcp-inspector` binary. Without a global install, prefix each command with `npx @modelcontextprotocol/inspector` instead, as above.

## Choosing a server

The CLI accepts a positional command (stdio), a `--server-url` (HTTP/SSE), or a named server out of a catalog or config file:

```bash
# stdio: everything positional is the command to spawn
mcp-inspector --cli node build/index.js --method tools/list

# HTTP
mcp-inspector --cli https://api.example.com/mcp --transport http --method tools/list

# From a file
mcp-inspector --cli --config ./mcp.json --server myserver --method tools/list
```

When the server comes from a file, its per-server settings (headers, timeouts, OAuth, [protocol era](/docs/draft/tools/inspector/protocol-eras), and roots) apply to the connection, resolved exactly as the TUI and web client resolve them. A `--header` flag overrides the file's headers for that run while leaving its timeouts and OAuth in place.

Later examples abbreviate whichever of these forms you use, along with its `--transport` or `--config`/`--server` flags, as `<server>`.

<Note>
  **The config file is the only durable way to give a run its
  [roots](/specification/draft/client/roots):** there is no roots flag, and the
  CLI has no `roots/set` method. Roots configured for a server are advertised at
  connect, so a server that calls `roots/list` (as
  `@modelcontextprotocol/server-filesystem` does, to learn its allowed
  directories) gets them.
</Note>

See [Configuration and flags](/docs/draft/tools/inspector/configuration) for `--catalog` vs. `--config`, the `--` separator, and the shared server-selection flags.

## Methods

| `--method`                 | Required companions                                            | Notes                                                                                   |
| -------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `initialize`               | None                                                           | Connect-only probe: `{serverInfo, protocolVersion, capabilities, instructions}`.        |
| `tools/list`               | None                                                           | `--strict` turns its schema portability check into a gate (see [CI gates](#ci-gates)).  |
| `tools/call`               | `--tool-name`, plus optional `--tool-arg` / `--tool-args-json` | `--load` calls it repeatedly (see [Load testing a tool](#load-testing-a-tool)).         |
| `resources/list`           | None                                                           |                                                                                         |
| `resources/read`           | `--uri`                                                        |                                                                                         |
| `resources/templates/list` | None                                                           |                                                                                         |
| `resources/directory/read` | `--uri`, plus optional `--cursor`                              | One page at a time; pass back the previous page's `nextCursor`.                         |
| `prompts/list`             | None                                                           |                                                                                         |
| `prompts/get`              | `--prompt-name`, plus optional `--prompt-args`                 |                                                                                         |
| `logging/setLevel`         | `--log-level`                                                  | Legacy era only; modern servers opt in per request instead.                             |
| `skills/list`              | None                                                           | `--verify` checks the skills returned (see [CI gates](#ci-gates)).                      |
| `skills/get`               | `--uri`                                                        | Same `--verify` option.                                                                 |
| `servers/list`             | None                                                           | Read the catalog **without connecting** to anything.                                    |
| `servers/show`             | `--server`                                                     | Same, for one entry.                                                                    |
| `servers/add`              | `--server`, plus a positional target or `--server-url`         | Write the catalog without connecting (see [Editing the catalog](#editing-the-catalog)). |
| `servers/edit`             | `--server`, plus what to change                                | Same.                                                                                   |
| `servers/remove`           | `--server`                                                     | Same.                                                                                   |

Stream- or session-only methods (`logging/tail`, for example) are rejected, since a process that exits can't hold a stream open.

### Passing arguments

`--tool-arg` takes `key=value` and **coerces** each value by JSON-parsing it when it parses, so `count=1` and `zip=10001` both send numbers. A value that is not valid JSON (`zip=012`, a bare word) is sent as a string, and a string is then converted to the type the tool's input schema declares for that property, so `zip=012` against a numeric `zip` still sends `12`:

```bash
mcp-inspector --cli <server> --method tools/call --tool-name mytool \
  --tool-arg key=value --tool-arg count=1 --tool-arg 'options={"format":"json"}'
```

`--tool-args-json` takes the whole argument object at once and skips the `key=value` parsing, so `{"zip":"10001"}` sends the string `"10001"` rather than a number. The schema conversion still applies to string values, so this only keeps a string a string when the schema types that property as a string (or doesn't declare it). The two flags are mutually exclusive:

```bash
mcp-inspector --cli <server> --method tools/call --tool-name mytool \
  --tool-args-json '{"zip":"10001"}'
```

## Output

`--format text` (the default) pretty-prints for humans. `--format json` emits a single JSON object on stdout with no banners, so the whole output pipes cleanly:

```bash
mcp-inspector --cli <server> --method tools/list --format json | jq '.result.tools[].name'
```

## Probing MCP Apps

`--app-info` reports whether a tool ships an [MCP App](/extensions/apps/overview) UI (its `ui://` resource, CSP, and permissions) **without calling the tool**, so a pipeline can decide whether it needs a browser before invoking anything:

```bash
# One tool -> one JSON line
mcp-inspector --cli <server> --method tools/call --tool-name my_tool --app-info
# {"hasApp":true,"toolName":"my_tool","resourceUri":"ui://...","csp":{...},"permissions":{...}}

# Every tool -> NDJSON, one line each, over a single connection
mcp-inspector --cli <server> --method tools/list --app-info | jq -c 'select(.hasApp)'
```

Exit codes distinguish the outcomes: a tool with an app exits `0`, one with no app exits `2`, and a missing tool exits `5`, so a typo isn't mistaken for "no app". A probe failure (unreadable UI resource, malformed `resourceUri`) is reported in a `resourceError` field rather than aborting, so one bad tool never kills a whole listing.

The CLI can't render an App, so by default it doesn't advertise the MCP Apps extension at `initialize`. A server that exposes its App tools only to clients claiming App support will then look app-less (exit `2`). Add `--advertise-apps` to claim the extension for that run.

<Note>
  `tools/list --app-info` always emits NDJSON (one line per tool) regardless of
  `--format`; `--format json` reshapes only the single-tool output of
  `tools/call --app-info`.
</Note>

## Load testing a tool

`--load` aims the CLI's own connection at one tool, with its transport, headers and OAuth, and keeps calling it. You can see how a server behaves under concurrent or sustained traffic without rebuilding that setup in a separate script. When the run ends, the CLI prints one latency and error-rate summary in place of a result. Every call sends the same arguments and `_meta`. [mcpdo](/docs/draft/tools/inspector/mcpdo#load-testing) runs the same engine against an open connection.

```bash
# 20 calls in flight for 30 seconds
mcp-inspector --cli <server> --method tools/call --tool-name search \
  --tool-arg query=mcp --load --load-concurrency 20 --load-duration 30

# exactly 500 calls, started at no more than 50 per second
mcp-inspector --cli <server> --method tools/call --tool-name search \
  --tool-arg query=mcp --load --load-requests 500 --load-rate 50
```

| Flag                               | Meaning                                                                                                                                                           |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--load`                           | Load-test the tool instead of calling it once. Requires `--method tools/call --tool-name <name>`.                                                                 |
| `--load-concurrency <n>`           | The most calls in flight at once (default `10`).                                                                                                                  |
| `--load-duration <sec>`            | Stop _starting_ calls after this many seconds. Calls already in flight still finish. Default `10` when `--load-requests` is not set.                              |
| `--load-requests <n>`              | Stop after starting this many calls. With `--load-duration` too, whichever is reached first ends the run.                                                         |
| `--load-rate <n>`                  | Start at most this many calls per second across all workers, spaced evenly (default unlimited).                                                                   |
| `--load-connections <n>`           | Spread the calls over this many independent sessions (default `1`, at most `--load-concurrency`, HTTP and SSE only). See [Multiple sessions](#multiple-sessions). |
| `--load-max-error-rate <fraction>` | Exit `10` when the share of failed calls is above this value (`0` to `1`). See [Thresholds](#thresholds).                                                         |
| `--load-max-p99 <ms>`              | Exit `10` when the p99 latency of the successful calls is above this many milliseconds, or when no call succeeded.                                                |

Each `--load-*` flag requires `--load`. `--load` is rejected with any method other than `tools/call`, and with `--app-info`, `--output`, `--output-format`, `--list-stored-auth` and `--print-handoff`. Each of those mistakes exits `1` with the envelope `code` `load_flag_conflict`.

### The summary

The summary goes to stdout. With `--format json` it is wrapped in `{ "result": … }`:

```json
{
  "tool": "search",
  "concurrency": 20,
  "durationMs": 30000,
  "requests": 41210,
  "ok": 41187,
  "toolErrors": 0,
  "errors": 23,
  "errorRate": 0.0006,
  "elapsedMs": 30012.4,
  "throughput": 1373.12,
  "okThroughput": 1372.35,
  "latencyMs": {
    "min": 2.1,
    "mean": 14.5,
    "p50": 12.9,
    "p90": 22.4,
    "p99": 61.3,
    "max": 212.8
  },
  "errorLatencyMs": {
    "min": 30001.2,
    "mean": 30003.1,
    "p50": 30002.9,
    "p90": 30004.1,
    "p99": 30004.8,
    "max": 30004.8
  },
  "errorMessages": [{ "message": "Request timed out", "count": 23 }],
  "toolErrorMessages": []
}
```

- **`toolErrors`** counts results that carry `isError: true`, meaning the tool ran and reported a failure. **`errors`** counts calls that never produced a result, such as protocol errors, request timeouts or a dropped connection. `errorRate` is both together over `requests`, rounded to four places.
- **`errorMessages`** groups the thrown messages by frequency. It keeps the first ten distinct messages and counts any others under `(other)`. **`toolErrorMessages`** does the same for `isError` results, using the first text block of each, so a run where every call returned `rate limited` says so.
- **Latency** is measured per call on the client, in milliseconds, with nearest-rank percentiles. `latencyMs` covers the successful calls only, and `errorLatencyMs` covers the failed ones, so failures that return instantly can't make a struggling server look fast. Either is `null` when it has no calls. `throughput` counts every completed call per second, and `okThroughput` counts only the successful ones.
- **`plannedStarts`, `droppedSlots` and `achievedRate`** appear only with `--load-rate`. Starts follow an even `1/rate` grid. A slot missed because every worker was busy is dropped rather than made up later, so a stall is never followed by a burst. A server too slow for the target rate can then report healthy latency while most of the planned load never ran, so when fewer than 90% of `plannedStarts` were started, a warning goes to stderr (dropped by `--quiet`). Raise `--load-concurrency` or lower the rate. Rates in the high hundreds per second and above are reached only approximately.
- **`stoppedEarly`** appears when the run ended before its bounds. Its `reason` is `consecutive_errors` when the server looks gone (50 thrown calls in a row, or a full second of nothing but thrown calls), or `interrupted` after Ctrl+C or SIGTERM. A tool error is the server answering, so it does not count toward the first.
- **`connections`** appears only with `--load-connections` above `1`.

`--load-duration` stops new calls, but calls in flight are allowed to finish, so `elapsedMs` can exceed the window by up to one call. Each call is still bounded by the server's request timeout (`requestTimeout` in the catalog or config file).

### When a run fails or stops

The tool is looked up once before the clock starts, so a missing tool exits `5` instead of reporting a 100% error rate. Otherwise a completed run exits `0` whatever its error rate, because the summary is the result, unless a [threshold](#thresholds) is set.

The first Ctrl+C or SIGTERM stops new calls, lets the in-flight ones finish, prints the summary of what completed, and exits `130` (envelope `code` `interrupted`) without checking any threshold. A second Ctrl+C exits `130` immediately.

A load run does not prompt for OAuth step-up. A tool that needs scopes the session lacks fails every call, and the challenge shows in `errorMessages`. Run one plain `tools/call` of the tool first to grant the scopes, then load it.

### Thresholds

Set a threshold to gate a CI job on the run without parsing the summary:

```bash
# fail the job if more than 1% of calls fail, or p99 is above 250 ms
mcp-inspector --cli <server> --method tools/call --tool-name search \
  --tool-arg query=mcp --load --load-requests 1000 \
  --load-max-error-rate 0.01 --load-max-p99 250
```

- The full summary prints first either way. A breach then exits `10` with an error envelope on stderr whose `code` is `load_error_rate_exceeded` or `load_p99_exceeded`. When both are breached, the message lists both and the `code` is `load_error_rate_exceeded`.
- A value equal to the threshold passes. The error-rate check uses the exact share of failed calls (`toolErrors` plus `errors`, over `requests`), not the rounded `errorRate`, so `--load-max-error-rate 0` fails on a single failure.
- `--load-max-p99` judges the successful calls, so a run where half the calls fail instantly can't pass on the speed of its failures. A run where no call succeeded has no p99 and fails.

### Multiple sessions

By default all calls share one connection, so a run measures how a server copes with concurrent requests on a single session. `--load-connections <n>` opens `n` independent connections with the same transport, headers and OAuth. Use it to see per-session state, session setup cost, connection limits and contention that only appear across sessions.

- **HTTP and SSE only.** Over stdio, every connection would spawn its own server process, which tests `n` isolated servers rather than one server under `n` sessions. More than one connection over stdio exits `1` (`load_flag_conflict`).
- **`--load-concurrency` and `--load-rate` are totals across all connections.** Workers are split as evenly as the counts allow, so `--load-connections` can't exceed `--load-concurrency`.
- **Setup is excluded from latency.** Every connection opens before the clock starts. Their connect times are reported separately in `connections.connectMs`.
- **A connection that fails to open is not a call error.** The run continues on the connections that opened, and the failures are counted under `connections`, never in `errors` or `errorRate`:

  ```json
  "connections": {
    "requested": 50,
    "opened": 48,
    "failed": 2,
    "connectMs": { "min": 8.2, "mean": 21.7, "p50": 19.4, "p90": 33.0, "p99": 41.8, "max": 41.8 },
    "errorMessages": [{ "message": "Too many sessions", "count": 2 }]
  }
  ```

- **OAuth.** The extra connections reuse the first connection's token and never start a sign-in of their own. Against a server that rotates refresh tokens, two connections refreshing an expired token at the same moment can lose a refresh, which shows up as call errors.

## Exit codes and error envelopes

Every non-zero exit maps to a stable failure class, so a caller can branch on _why_ without scraping prose:

| Code  | Meaning                                                                                                                                                                                                          |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`   | Success.                                                                                                                                                                                                         |
| `1`   | Usage or unexpected error (the catch-all), including an unreadable secret store or OAuth state file.                                                                                                             |
| `2`   | No MCP App found on the tool (`--app-info` probe).                                                                                                                                                               |
| `3`   | Server requires authentication (HTTP 401/403, or an SDK authorization error).                                                                                                                                    |
| `4`   | Server unreachable (DNS, connection refused, timeout, `fetch failed`).                                                                                                                                           |
| `5`   | Tool error: `tools/call` returned `isError: true`, or the tool wasn't found.                                                                                                                                     |
| `6`   | `--strict` found an error-severity tool-schema portability problem.                                                                                                                                              |
| `7`   | `--verify` found a skill that violates SEP-2640 (conformance, digest, or size mismatch).                                                                                                                         |
| `8`   | `--verify` couldn't check every skill within its read bounds.                                                                                                                                                    |
| `9`   | `--verify --require-digests` found a skill that advertises no digests.                                                                                                                                           |
| `10`  | A `--load` run breached a `--load-max-error-rate` or `--load-max-p99` threshold. The summary is printed first, and the envelope `code` names the threshold: `load_error_rate_exceeded` or `load_p99_exceeded`.   |
| `11`  | The server answered HTTP 429 (envelope `code` `rate_limited`). The envelope also carries `method`, plus `retryAfter` (the `Retry-After` header as sent) and `retryAfterMs` when the server sent one that parses. |
| `130` | A `--load` run was interrupted by Ctrl+C or SIGTERM (envelope `code` `interrupted`). The summary of what completed is printed first.                                                                             |

On any non-zero exit the CLI also writes a **single JSON line to stderr**:

```json
{
  "error": {
    "code": "auth_required",
    "message": "Unauthorized",
    "status": 401,
    "url": "https://api.example/mcp"
  }
}
```

The envelope carries `code` and `message` always, plus `cause` (the underlying error, such as a DNS failure), `status` (the HTTP status) and `url` when known. Query-string secrets in a URL are redacted. `code` is a stable name for the failure: `auth_required`, `unreachable`, `tool_not_found`, `tool_is_error`, `no_app`, `schema_unportable`, `store_unavailable`, `oauth_state_unrecognized`, `rate_limited`, or the catch-all `error`, among others.

Because it's one line, a caller can parse it with `2>&1 | tail -1 | jq .error`.

A `tools/call` that returns `isError: true` still prints its payload, but exits `5`, so an `&&` chain doesn't proceed on a failed call.

## Authorization in scripts

By default the CLI runs the same loopback OAuth flow as the TUI: it opens a browser and waits on a localhost callback that a CI job can't complete. Two flags make non-interactive runs predictable:

- `--stored-auth-only`: never start interactive OAuth or step-up, and never auto-open a browser. Use tokens from the shared store if present, otherwise fail immediately with `auth_required`. This is the flag CI wants.
- `--use-stored-auth`: reuse a token that the web Inspector already obtained on this machine, refreshing it first when a refresh token is stored. It looks the token up by URL, so it requires `--server-url`.

Without either, and with no TTY on stdin or stderr, the CLI fails fast with `auth_required` rather than hanging for fifteen minutes on a callback nobody will complete.

See [Authorization](/docs/draft/tools/inspector/authorization) for the full flow, the web-to-CLI handoff, and `--print-handoff`.

## Recipes

### Verify a server in CI

```bash
set -euo pipefail

# Fail the build if the server can't be reached or doesn't expose the tool
mcp-inspector --cli --config ./ci-servers.json --server my-server \
  --stored-auth-only --method tools/list --format json \
  | jq -e '.result.tools | map(.name) | index("get_weather")' > /dev/null
```

### CI gates

These flags turn a check into a non-zero exit, each with its own code so a job can tell the failures apart:

- `--strict` (with `tools/list`): reports tool-schema portability problems in full on stderr (path, issue, suggested fix) and exits `6` if any is error-severity. Without it, `tools/list` prints only a one-line count. Under `--format json` the findings are folded into the output as `schemaFindings`.
- `--verify` (with `skills/list` or `skills/get`): runs the SEP-2640 conformance and digest checks, writes one JSON report per skill on stdout, and exits `7` on a violation or `8` when the read bounds stopped it before every skill was checked. `--skill-catalog-max-skills` and `--skill-catalog-max-bytes` set those bounds.
- `--require-digests` (with `--verify`): exits `9` for a skill that advertises no digests, instead of reporting it as unverifiable and exiting `0`.
- `--load-max-error-rate <fraction>` and `--load-max-p99 <ms>` (with `--load`): print the load run's summary, then exit `10` when the share of failed calls is above the fraction, or the p99 latency of the successful calls is above the given milliseconds. See [Thresholds](#thresholds).

```bash
mcp-inspector --cli <server> --method tools/list --strict > /dev/null
mcp-inspector --cli <server> --method skills/list --verify --require-digests
mcp-inspector --cli <server> --method tools/call --tool-name get_weather --load --load-requests 200 --load-max-p99 500
```

### Branch on the failure class

```bash
if out=$(mcp-inspector --cli "$URL" --transport http --method tools/list 2>err.json); then
  echo "$out"
else
  case $? in
    3) echo "needs auth: run the web inspector once to sign in" ;;
    4) echo "server unreachable" ;;
    *) jq .error < err.json ;;
  esac
fi
```

### Smoke-test every tool that has a UI

```bash
mcp-inspector --cli "$URL" --transport http --method tools/list --app-info \
  | jq -r 'select(.hasApp) | .toolName'
```

### Inspect a catalog without connecting

```bash
mcp-inspector --cli --catalog ~/.mcp-inspector/mcp.json --method servers/list
mcp-inspector --cli --catalog ~/.mcp-inspector/mcp.json --method servers/show --server my-server
```

<Warning>
  `servers/show` redacts secret-bearing fields (`env` values, sensitive headers,
  OAuth client secrets), but it does **not** scrub credentials embedded in a
  server `url` (userinfo or query tokens) or in stdio `args`. Treat raw URL and
  `detail` fields as sensitive before pasting them into an issue.
</Warning>

### Editing the catalog

`servers/add`, `servers/edit`, and `servers/remove` write the catalog without connecting to anything. They go through the same code as the web client's server list, so `env` values and client secrets land in the [secret store](/docs/draft/tools/inspector/configuration#where-secrets-are-stored) exactly as they would from the UI, and a running web client picks up the change.

```bash
# Add: the positional target or --server-url describes the entry, not a server to connect to
mcp-inspector --cli node build/index.js -e API_KEY=secret --method servers/add --server my-server

# Edit: change the target, -e, --cwd, --header, or --protocol-era, or rename it
mcp-inspector --cli --method servers/edit --server my-server --rename my-renamed-server

# Remove the entry and its stored secrets
mcp-inspector --cli --method servers/remove --server my-renamed-server
```

Only the writable catalog (`--catalog`, `MCP_CATALOG_PATH`, or the default) can be written; `--config` is refused. With an in-memory secret store, a write that supplies `-e` values (and a `--rename`) is refused, since the secrets would be lost when the run exits.

## Proxies

Connections to remote HTTP/SSE servers honor the conventional proxy variables: `HTTPS_PROXY` / `HTTP_PROXY` (and their lowercase forms) select the proxy and `NO_PROXY` exempts hosts. No Inspector-specific flag is needed, and the proxy agent is loaded lazily, so runs without a proxy pay nothing. The same applies to the web client's backend.
