title: Understanding Authorization in MCP
description: Learn how to implement secure authorization for MCP servers using OAuth 2.1 to protect sensitive resources and operations

Authorization in the Model Context Protocol (MCP) secures access to sensitive resources and operations exposed by MCP servers. If your MCP server handles user data or administrative actions, authorization ensures only permitted users can access its endpoints.

MCP builds on [OAuth 2.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13) conventions to let clients and servers establish trust in a consistent way, without depending on one specific identity provider or auth system. For the full details, see the [Authorization specification](/specification/2026-07-28/basic/authorization).

## When Should You Use Authorization?

While authorization for MCP servers is **optional**, it is strongly recommended when:

- Your server works with user-specific data like emails, documents, or databases
- You need to track which user performed a given action
- Your server exposes APIs that require user consent before access
- You're targeting enterprise environments with strict access controls
- You want to rate-limit or track usage on a per-user basis

<Tip>
**Authorization for Local MCP Servers**

MCP servers using the [STDIO transport](/specification/2026-07-28/basic/transports/stdio) run locally, so they can acquire user credentials from the environment or from third-party libraries embedded in the server instead. OAuth flows are designed for HTTP-based transports where the client must establish that a user is authorized to access a remotely-hosted server.

</Tip>

## The Authorization Flow: Step by Step

Let's walk through what happens when a client wants to connect to your protected MCP server:

<Steps>
<Step title="Initial Handshake">
When your MCP client first tries to connect, your server responds with a `401 Unauthorized` and tells the client where to find authorization information, captured in a [Protected Resource Metadata (PRM) document](https://datatracker.ietf.org/doc/html/rfc9728). The document is hosted by the MCP server, follows a predictable path pattern, and can be provided to the client in the `resource_metadata` parameter within the `WWW-Authenticate` header.

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="mcp",
  resource_metadata="https://your-server.com/.well-known/oauth-protected-resource",
  scope="mcp:tools mcp:resources"
```

This tells the client that authorization is required for the MCP server, where to get the necessary information to kickstart the authorization flow, and which scopes are needed to access the resource. For more on how clients should select scopes, see the [Scope Selection Strategy](/specification/2026-07-28/basic/authorization#scope-selection-strategy) section in the authorization spec.

The `WWW-Authenticate` pointer is optional. Servers can instead serve the PRM document only at the well-known URIs. When the header carries no `resource_metadata` parameter, clients must fall back to those URIs, trying the path-inserted form (for example, `https://your-server.com/.well-known/oauth-protected-resource/mcp`) before the root `https://your-server.com/.well-known/oauth-protected-resource`. See [Protected Resource Metadata Discovery Requirements](/specification/2026-07-28/basic/authorization/authorization-server-discovery#protected-resource-metadata-discovery-requirements) for the details.

</Step>

<Step title="Protected Resource Metadata Discovery">
With the URI pointer to the PRM document, the client will fetch the metadata to learn about the authorization server, supported scopes, and other resource information. The data is typically encapsulated in a JSON blob, similar to the one below.

```json
{
  "resource": "https://your-server.com/mcp",
  "authorization_servers": ["https://auth.your-server.com"],
  "scopes_supported": ["mcp:tools", "mcp:resources"]
}
```

You can see a more comprehensive example in [RFC 9728 Section 3.2](https://datatracker.ietf.org/doc/html/rfc9728#name-protected-resource-metadata-r).

</Step>

<Step title="Authorization Server Discovery">
Next, the client discovers what the authorization server can do by fetching its metadata. If the PRM document lists more than one authorization server, the client can decide which one to use. Clients must keep registration state (client credentials, tokens) separate per authorization server, keyed by its `issuer` identifier, and must not reuse credentials across authorization servers. See [Authorization Server Location](/specification/2026-07-28/basic/authorization/authorization-server-discovery#authorization-server-location) for the requirements.

With an authorization server selected, the client will then construct a standard metadata URI and issue a request to the [OpenID Connect (OIDC) Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html) or [OAuth 2.0 Auth Server Metadata](https://datatracker.ietf.org/doc/html/rfc8414) endpoints (depending on authorization server support) and retrieve another set of metadata properties that will allow it to know the endpoints it needs to complete the authorization flow.

```json
{
  "issuer": "https://auth.your-server.com",
  "authorization_endpoint": "https://auth.your-server.com/authorize",
  "token_endpoint": "https://auth.your-server.com/token",
  "registration_endpoint": "https://auth.your-server.com/register",
  "client_id_metadata_document_supported": true
}
```

</Step>

<Step title="Client Registration">
With all the metadata out of the way, the client now needs to make sure that it's registered with the authorization server. MCP supports three client registration mechanisms:

| Approach                         | When to Use                                                  |
| -------------------------------- | ------------------------------------------------------------ |
| **Client ID Metadata Documents** | When client and server have no prior relationship            |
| **Pre-registration**             | When client and server have an existing relationship         |
| **Dynamic Client Registration**  | For backwards compatibility with older authorization servers |

See [Client Registration Approaches](#client-registration-approaches) below for a summary of each mechanism.

</Step>

<Step title="User Authorization">
The client will now need to open a browser to the `/authorize` endpoint, where the user can log in and grant the required permissions. The authorization server will then redirect back to the client with an authorization code that the client exchanges for tokens:

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "refresh_token": "def502...",
  "token_type": "Bearer",
  "expires_in": 3600
}
```

The access token is what the client will use to authenticate requests to the MCP server. This step follows standard [OAuth 2.1 authorization code with PKCE](https://oauth.net/2/grant-types/authorization-code/) conventions. PKCE helps prevent authorization code interception and injection attacks by requiring clients to create a secret verifier-challenge pair, ensuring that only the original requestor can exchange an authorization code for tokens.

</Step>

<Step title="Making Authenticated Requests">
Finally, the client can make requests to your MCP server using the access token embedded in the `Authorization` header:

```http
GET /mcp HTTP/1.1
Host: your-server.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...
```

The MCP server will need to validate the token and process the request if the token is valid and has the required permissions.

If a later operation needs permissions the token does not carry, the server responds with a `403 Forbidden` and an `insufficient_scope` challenge that should list the scopes the operation requires. The client then re-authorizes with the union of its previously requested scopes and the challenged scopes, so permissions granted earlier are not lost. See [Scope Challenge Handling](/specification/2026-07-28/basic/authorization#scope-challenge-handling) in the authorization spec for the step-up authorization flow.

</Step>
</Steps>

## Client Registration Approaches

MCP supports three client registration mechanisms to accommodate different deployment scenarios. [Client Registration](/specification/2026-07-28/basic/authorization/client-registration) in the authorization spec defines the requirements for each, including the recommended fallback order when a client supports more than one. Here is how they compare in practice.

### Client ID Metadata Documents

<Note>This is the recommended approach for client registration in MCP.</Note>

Client ID Metadata Documents ([draft-ietf-oauth-client-id-metadata-document-00](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00)) allow MCP clients to use an HTTPS URL as their `client_id`. The client hosts a JSON document with its metadata (name, redirect URIs, and so on) at that URL. When authorization starts, the authorization server detects the URL format, fetches the document, validates it, and uses the metadata to process the request. No pre-existing relationship between client and server is required, and the authorization server stores no client registrations.

Client IDs based on metadata documents are also portable across authorization servers, since they are self-hosted HTTPS URLs resolved on demand. No re-registration is needed when the authorization server changes.

For the document requirements, the validation rules, and an example metadata document, see [Client ID Metadata Documents](/specification/2026-07-28/basic/authorization/client-registration#client-id-metadata-documents) in the authorization spec.

### Pre-Registration

Pre-registration is appropriate when the client and authorization server have an existing relationship. The client can carry embedded registration information (a client ID and, if applicable, client credentials), or offer a UI that allows users to enter these details after registering an OAuth client themselves.

Pre-registered credentials are specific to the authorization server that issued them. If the authorization server advertised by the MCP server changes, the client must not reuse the old credentials with the new server. See [Pre-registration](/specification/2026-07-28/basic/authorization/client-registration#pre-registration) in the authorization spec.

### Dynamic Client Registration

<Warning>
  This is a legacy approach maintained for backwards compatibility with earlier
  versions of the MCP authorization specification. New implementations should
  prefer Client ID Metadata Documents when the authorization server supports
  them.
</Warning>

Dynamic Client Registration ([RFC7591](https://datatracker.ietf.org/doc/html/rfc7591)) allows clients to programmatically register with an authorization server by sending a request containing their metadata to the `registration_endpoint`. Use it when the authorization server does not support Client ID Metadata Documents, when you're integrating with legacy systems, or when the authorization server requires server-side client registration for policy reasons.

Unauthenticated DCR means anyone can register any client with the authorization server, so authorization servers should implement appropriate controls such as trusted hosts and rate limiting. Credentials obtained through DCR are also bound to the authorization server that issued them and must not be reused across authorization servers. See [Dynamic Client Registration](/specification/2026-07-28/basic/authorization/client-registration#dynamic-client-registration) in the authorization spec for the full requirements, including the `application_type` constraints that apply when registering with OIDC authorization servers, and [Authorization Server Binding](/specification/2026-07-28/basic/authorization/client-registration#authorization-server-binding) for how clients must key their registration state.

## Implementing Authorization

The rest of this tutorial sets up end-to-end authorization for an MCP server that uses CIMD for client registration.

### Authorization Server Requirements

Validating URL-based client IDs is entirely the authorization server's job, so most of the setup happens there. Any CIMD-capable authorization server works, whether it is a managed identity platform or software you host yourself. Whatever you pick has to meet the requirements below.

The authorization server must accept HTTPS URLs as `client_id` values and advertise that support by including `client_id_metadata_document_supported: true` in its authorization server metadata. Clients read this flag to decide whether to use CIMD or fall back to another registration approach. On managed platforms this is typically a project setting you enable. If the flag is absent, clients will not attempt CIMD and the authorization server will reject URL-shaped client IDs.

It must issue the scopes your MCP server advertises. Define a scope such as `mcp:tools` and configure the authorization server to include it in the `scope` claim of issued access tokens. How scopes are modeled varies by provider. Some map them onto roles and permissions, others treat them as plain strings. The result is the same: a client that requests `mcp:tools` and receives user consent gets a token carrying that scope.

It must bind tokens to your MCP server. Clients send a `resource` parameter identifying the MCP server ([RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707)), and the authorization server should reflect it in the token's audience (`aud`) claim. Your MCP server rejects tokens minted for other resources, so an authorization server that only issues fixed or generic audiences will fail validation.

Finally, it must handle user login and consent. When the client opens the authorization endpoint in a browser, the authorization server authenticates the user, shows the requested scopes, and records consent. Some providers host this experience for you, while others expect you to run a small web app that renders their login flow and drives their authorization API. Once the user approves, the authorization server redirects back to the client's `redirect_uri` with an authorization code.

### Write the MCP Server

Your MCP server acts as an OAuth 2.1 resource server. It validates access tokens and serves Protected Resource Metadata so clients know where to authenticate. The SDK handles the metadata endpoints and `WWW-Authenticate` challenges for you.

The MCP server contains no CIMD-specific code. When a client presents a URL-shaped `client_id`, the authorization server fetches the metadata document from that URL and applies the validation the client registration spec requires of authorization servers, including the exact `client_id` match and the `redirect_uri` check against the document's `redirect_uris`. The MCP server only needs to point clients at the authorization server. The examples below use `https://auth.example.com` as the authorization server URL, so replace it with your own.

<Tabs>
<Tab title="TypeScript">

In TypeScript, the server fetches the authorization server metadata once at startup, validates incoming JWTs against the JWKS endpoint listed there, and serves the discovery metadata with `mcpAuthMetadataRouter`. The example needs `zod` 4, since `@modelcontextprotocol/server` depends on `zod ^4` and `registerTool` won't type-check against `zod` 3 (install with `npm install @modelcontextprotocol/server @modelcontextprotocol/node @modelcontextprotocol/express jose zod@4`):

```typescript
import { McpServer, checkResourceAllowed } from "@modelcontextprotocol/server";
import type { OAuthMetadata } from "@modelcontextprotocol/server";
import { NodeStreamableHTTPServerTransport } from "@modelcontextprotocol/node";
import {
  createMcpExpressApp,
  mcpAuthMetadataRouter,
  requireBearerAuth,
  getOAuthProtectedResourceMetadataUrl,
} from "@modelcontextprotocol/express";
import { createRemoteJWKSet, jwtVerify } from "jose";
import { z } from "zod";

const AUTH_SERVER_URL = "https://auth.example.com";
const SERVER_URL = new URL("http://localhost:3001");

// Fetch the authorization server metadata, including
// client_id_metadata_document_supported: true. The metadata router derives
// the Protected Resource Metadata document from it and re-serves it at this
// origin for legacy clients.
const metadataResponse = await fetch(
  `${AUTH_SERVER_URL}/.well-known/oauth-authorization-server`,
);
const oauthMetadata = (await metadataResponse.json()) as OAuthMetadata;

// The metadata lists where the authorization server publishes its signing keys
if (typeof oauthMetadata.jwks_uri !== "string") {
  throw new Error("Authorization server metadata is missing jwks_uri");
}
const JWKS = createRemoteJWKSet(new URL(oauthMetadata.jwks_uri));

const tokenVerifier = {
  verifyAccessToken: async (token: string) => {
    const { payload } = await jwtVerify(token, JWKS, {
      issuer: oauthMetadata.issuer,
    });

    // Reject tokens that were not issued for this server (RFC 8707)
    const audiences = Array.isArray(payload.aud)
      ? payload.aud
      : payload.aud
        ? [payload.aud]
        : [];
    const audienceAllowed = audiences.some((aud) => {
      try {
        return checkResourceAllowed({
          requestedResource: aud,
          configuredResource: SERVER_URL,
        });
      } catch {
        // Audience values that are not URLs can never be our resource,
        // so treat them as "no match" instead of crashing.
        return false;
      }
    });
    if (!audienceAllowed) {
      throw new Error("Token audience does not match this server");
    }

    return {
      token,
      clientId: (payload.sub as string) ?? "",
      scopes: typeof payload.scope === "string" ? payload.scope.split(" ") : [],
      expiresAt: payload.exp,
    };
  },
};

const app = createMcpExpressApp();

app.use(
  mcpAuthMetadataRouter({
    oauthMetadata,
    resourceServerUrl: SERVER_URL,
    scopesSupported: ["mcp:tools"],
    resourceName: "Example MCP Server",
  }),
);

// Require a valid bearer token on the MCP endpoint. Requests without one
// receive a 401 with a WWW-Authenticate challenge pointing at the PRM document.
const authMiddleware = requireBearerAuth({
  verifier: tokenVerifier,
  requiredScopes: [],
  resourceMetadataUrl: getOAuthProtectedResourceMetadataUrl(SERVER_URL),
});

app.all("/", authMiddleware, async (req, res) => {
  const server = new McpServer({ name: "example-server", version: "1.0.0" });

  server.registerTool(
    "add",
    {
      title: "Addition Tool",
      description: "Add two numbers together",
      inputSchema: z.object({
        a: z.number().describe("First number"),
        b: z.number().describe("Second number"),
      }),
    },
    async ({ a, b }) => ({
      content: [{ type: "text", text: `${a} + ${b} = ${a + b}` }],
    }),
  );

  const transport = new NodeStreamableHTTPServerTransport({
    sessionIdGenerator: undefined,
  });

  res.on("close", () => {
    transport.close().catch(() => {});
    server.close().catch(() => {});
  });

  await server.connect(transport);
  await transport.handleRequest(req, res, req.body);
});

app.listen(3001, () => {
  console.log("MCP server listening on http://localhost:3001");
});
```

`mcpAuthMetadataRouter` serves the Protected Resource Metadata document, which lists your authorization server. `requireBearerAuth` protects the MCP endpoint. It runs the verifier's `verifyAccessToken` on every request and answers unauthenticated or invalid ones with a `401` and a `WWW-Authenticate` challenge pointing at the Protected Resource Metadata. Inside `verifyAccessToken`, `checkResourceAllowed` rejects tokens whose `aud` claim does not match this server, as the spec requires.

The verifier above assumes the authorization server issues JWT access tokens. If yours issues opaque tokens, implement `verifyAccessToken` against its [token introspection](https://oauth.net/2/token-introspection/) endpoint and apply the same audience check to the introspection response.

For more details, see the [TypeScript SDK documentation](https://github.com/modelcontextprotocol/typescript-sdk).

<Tab title="Python">

In Python, the SDK serves the Protected Resource Metadata and answers unauthenticated requests with a `401` and a `WWW-Authenticate` challenge for you, so the server only needs a token verifier and its `AuthSettings`. The verifier below fetches the authorization server metadata once at startup and validates incoming JWTs against the JWKS endpoint listed there.

Install the SDK and a JWT library (the `crypto` extra is required to verify RS256 signatures):

```bash
pip install "mcp>=2.0" "pyjwt[crypto]"
```

Then write the server:

```python
"""OAuth-protected MCP server (Python)."""

import httpx2
import jwt
from jwt import PyJWKClient
from pydantic import AnyHttpUrl

from mcp.server.auth.provider import AccessToken, TokenVerifier
from mcp.server.auth.settings import AuthSettings
from mcp.server.mcpserver import MCPServer
from mcp.shared.auth_utils import check_resource_allowed, resource_url_from_server_url

AUTH_SERVER_URL = "https://auth.example.com"
SERVER_URL = "http://localhost:3001"


class JWTTokenVerifier(TokenVerifier):
    """Validate JWT access tokens against the authorization server's signing keys."""

    def __init__(self, auth_server_url: str, server_url: str) -> None:
        # Fetch the authorization server metadata once, which includes
        # client_id_metadata_document_supported: true and the jwks_uri where the
        # authorization server publishes its signing keys.
        metadata = httpx2.get(f"{auth_server_url}/.well-known/oauth-authorization-server").json()
        self.issuer = metadata["issuer"]
        self.jwks_client = PyJWKClient(metadata["jwks_uri"])
        self.resource_url = resource_url_from_server_url(server_url)

    async def verify_token(self, token: str) -> AccessToken | None:
        try:
            signing_key = self.jwks_client.get_signing_key_from_jwt(token)
            payload = jwt.decode(
                token,
                signing_key.key,
                algorithms=["RS256"],
                issuer=self.issuer,
                # Audience is checked below with RFC 8707 resource matching
                options={"verify_aud": False},
            )
        except jwt.PyJWTError:
            return None

        # Reject tokens that were not issued for this server (RFC 8707)
        audiences = payload.get("aud", [])
        if isinstance(audiences, str):
            audiences = [audiences]
        if not any(check_resource_allowed(aud, self.resource_url) for aud in audiences):
            return None

        return AccessToken(
            token=token,
            client_id=payload.get("client_id") or payload.get("sub", ""),
            scopes=payload.get("scope", "").split(),
            expires_at=payload.get("exp"),
            subject=payload.get("sub"),
        )


mcp = MCPServer(
    "Example MCP Server",
    token_verifier=JWTTokenVerifier(AUTH_SERVER_URL, SERVER_URL),
    auth=AuthSettings(
        issuer_url=AnyHttpUrl(AUTH_SERVER_URL),
        resource_server_url=AnyHttpUrl(SERVER_URL),
        required_scopes=["mcp:tools"],
    ),
)


@mcp.tool()
def add(a: float, b: float) -> float:
    """Add two numbers together."""
    return a + b


if __name__ == "__main__":
    mcp.run(transport="streamable-http")
```

The `AuthSettings` you pass to `MCPServer` drive the Protected Resource Metadata document, which lists your authorization server, and `required_scopes` are enforced on every request. Inside `verify_token`, `check_resource_allowed` rejects tokens whose `aud` claim does not match this server, as the spec requires, and any signature, issuer, or expiry failure returns `None`, which the SDK turns into a `401`.

The verifier above assumes the authorization server issues JWT access tokens. If yours issues opaque tokens, implement `verify_token` against its [token introspection](https://oauth.net/2/token-introspection/) endpoint and apply the same audience check to the introspection response.

Run the server with:

```bash
python server.py
```

For more details, see the [Python SDK documentation](https://github.com/modelcontextprotocol/python-sdk).

<Tab title="C#">

In C#, the MCP server points clients directly at the external authorization server. The `AddMcp()` extension configures Protected Resource Metadata, and the `McpAuthenticationHandler` automatically serves it and adds `WWW-Authenticate` headers on `401` responses. Token validation uses the built-in ASP.NET Core JWT bearer middleware.

In the root of your server folder, create two files, `Program.cs` and `ProtectedMcpServer.csproj`, and a `Tools` folder. Fill `Program.cs` with:

```csharp
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Tokens;
using ModelContextProtocol.AspNetCore.Authentication;
using ProtectedMcpServer.Tools;

var builder = WebApplication.CreateBuilder(args);

var serverUrl = "http://localhost:3001";
var authServerUrl = "https://auth.example.com";

builder.Services.AddAuthentication(options =>
{
    options.DefaultChallengeScheme = McpAuthenticationDefaults.AuthenticationScheme;
    options.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;
})
.AddJwtBearer(options =>
{
    options.Authority = authServerUrl;
    options.TokenValidationParameters = new TokenValidationParameters
    {
        ValidIssuer = authServerUrl,
        ValidAudience = serverUrl,
    };
})
.AddMcp(options =>
{
    options.ResourceMetadata = new()
    {
        Resource = serverUrl,
        AuthorizationServers = { authServerUrl },
        ScopesSupported = ["mcp:tools"],
    };
});

builder.Services.AddAuthorization();
builder.Services.AddMcpServer()
    .WithTools<MathTools>()
    .WithHttpTransport();

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

app.MapMcp().RequireAuthorization();

app.Run(serverUrl);
```

### Test the Flow

With the server running, connect an MCP client that supports the current authorization spec. In [Visual Studio Code](https://code.visualstudio.com), press <kbd>Cmd</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd>, select **MCP: Add server...**, choose **HTTP**, and enter `http://localhost:3001`. On connection, the authorization flow will proceed as follows:

1. The server returns a `401` with `WWW-Authenticate` pointing to the Protected Resource Metadata
2. The client fetches the PRM and discovers your authorization server
3. The authorization server metadata advertises `client_id_metadata_document_supported: true`
4. The client uses CIMD and initiates the OAuth flow
5. A browser window opens to the authorization server, where the user logs in and grants consent
6. After authentication, the client receives a token and retries the request

Once the connection succeeds, the client lists the server's tools and can invoke them with the issued token.

You can also use [client.dev](https://client.dev/) as a reference authorization server that supports CIMD out of the box for quick testing and experimentation.

<Note>
**Common Issues**

- The authorization server must be able to fetch the client's `client_id` URL. Verify the URL is reachable from the authorization server's network with `curl` or a browser.
- The `client_id` field in the metadata document must exactly match the URL where the document is hosted. Even trailing slash differences will cause validation failures.
- The metadata document must contain `client_id`, `client_name`, and `redirect_uris`.
- The metadata document URL must use HTTPS and include a path component.
- Custom scopes must be defined on the authorization server before clients can request them, or the authorization request is rejected.

</Note>

### Falling Back to Dynamic Client Registration

Not every authorization server supports CIMD yet. When `client_id_metadata_document_supported` is missing from the authorization server metadata, clients fall back to [Dynamic Client Registration](#dynamic-client-registration). Before starting the authorization flow, the client sends its metadata to the authorization server's `registration_endpoint` and receives a generated `client_id` in response.

The MCP server code above works unchanged. It advertises the authorization server in its Protected Resource Metadata and validates tokens the same way regardless of how the client registered. On the authorization server, enable Dynamic Client Registration, confirm the `registration_endpoint` appears in its metadata, and put controls such as trusted hosts and rate limiting around it, since unauthenticated registration is open to anyone.

## Common Pitfalls and How to Avoid Them

For comprehensive security guidance, including attack vectors, mitigation strategies, and implementation best practices, make sure to read through [Security Best Practices](/docs/2026-07-28/tutorials/security/security_best_practices). A few key issues are called out below.

- **Do not implement token validation or authorization logic by yourself**. Use off-the-shelf, well-tested, and secure libraries for things like token validation or authorization decisions. Doing everything from scratch means that you're more likely to implement things incorrectly unless you are a security expert.
- **Use short-lived access tokens**. Depending on the authorization server used, this setting might be customizable. We recommend to not use long-lived tokens - if a malicious actor steals them, they will be able to maintain their access for longer periods.
- **Always validate tokens**. Just because your server received a token does not mean that the token is valid or that it's meant for your server. Always verify that what your MCP server is getting from the client matches the required constraints.
- **Store tokens in secure, encrypted storage**. In certain scenarios, you might need to cache tokens server-side. If that is the case, ensure that the storage has the right access controls and cannot be easily exfiltrated by malicious parties with access to your server. You should also implement robust cache eviction policies to ensure that your MCP server is not re-using expired or otherwise invalid tokens.
- **Enforce HTTPS in production**. Do not accept tokens or redirect callbacks over plain HTTP except for `localhost` during development.
- **Least-privilege scopes**. Don't use catch‑all scopes. Split access per tool or capability where possible and verify required scopes per route/tool on the resource server.
- **Don't log credentials**. Never log `Authorization` headers, tokens, codes, or secrets. Scrub query strings and headers. Redact sensitive fields in structured logs.
- **Separate app vs. resource server credentials**. Don't reuse your MCP server's client secret for end‑user flows. Store all secrets in a proper secret manager, not in source control.
- **Return proper challenges**. On 401, include `WWW-Authenticate` with `Bearer`, `realm`, `resource_metadata`, and the `scope` needed for the resource so clients can discover how to authenticate and what to request. The `resource_metadata` pointer is optional, and clients fall back to the well-known URIs when it is absent, so make sure the Protected Resource Metadata document is served there.
- **Validate the `iss` on authorization responses**. Authorization servers should attach the `iss` parameter to authorization responses, including error responses, per [RFC 9207](https://datatracker.ietf.org/doc/html/rfc9207). Clients must compare a received `iss` against the issuer they recorded before redirecting, using simple string comparison, and reject the response on mismatch. See [Authorization Response Validation](/specification/2026-07-28/basic/authorization#authorization-response-validation).
- **DCR (Dynamic Client Registration) controls**. If using the legacy DCR approach, be aware of constraints specific to your organization, such as trusted hosts, required vetting, and audited registrations. Unauthenticated DCR means that anyone can register any client with your authorization server. Consider migrating to Client ID Metadata Documents for improved security and flexibility.
- **Multi‑tenant/realm mix-ups**. Pin to a single issuer/tenant unless explicitly multi‑tenant. Reject tokens from other realms even if signed by the same authorization server.
- **Audience/resource indicator misuse**. Don't configure or accept generic audiences (like `api`) or unrelated resources. Require the audience/resource to match your configured server.
- **Error detail leakage**. Return generic messages to clients, but log detailed reasons with correlation IDs internally to aid troubleshooting without exposing internals.
- **Never tie authorization to session identifiers**. Protocol revisions from 2026-07-28 onward remove protocol-level sessions. Servers that support only these revisions should ignore any `Mcp-Session-Id` header sent by older clients, and servers that still support earlier revisions must never derive authorization from it. If your server keeps its own application-level session state, treat identifiers as untrusted input and derive authorization decisions from the validated access token only.
