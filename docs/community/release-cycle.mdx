MCP specification releases are published every six months, generally on the last Tuesday of March and September.

## Schedule

Each release has an eight-month cycle. Planning for the next release starts two months before the current release is published. Release managers publish exact milestone dates and cutoff times on the [roadmap](/development/roadmap) at the start of planning. Milestone intervals are measured in calendar months.

Specification versions use the release date in [`YYYY-MM-DD` format](/docs/learn/versioning).

## Milestones

| Milestone                    | Before release | Outcome                                                                                                           |
| ---------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------- |
| Planning begins              | 8 months       | Core Maintainers propose a roadmap and gather feedback from maintainers and working groups.                       |
| Core Maintainer review opens | 6 months       | Priorities are published and scheduled SEP reviews begin.                                                         |
| Soft freeze                  | 2.5 months     | Review closes. Included SEPs must be [Final](/community/sep-guidelines#workflow) and merged.                      |
| Next-cycle planning begins   | 2 months       | Planning for the following release starts.                                                                        |
| SDK beta                     | 1.5 months     | Tier 1 SDKs publish betas supporting the frozen specification.                                                    |
| Hard freeze                  | 1 month        | Specification changes are restricted to emergency corrections.                                                    |
| Release                      | 0 months       | The specification, release notes, implementation and migration guidance, and SDK readiness summary are published. |

During planning, Core Maintainers publish priorities that cover the next six to twelve months and identify dependencies across working groups and SDKs. Proposals that align with the roadmap receive review priority, but a place on the roadmap does not guarantee acceptance or inclusion in a particular release.

At soft freeze, release managers publish the frozen scope and the list of deferred proposals. Between soft and hard freeze, changes are limited to bug fixes, polish, and clarifications within the frozen scope. New features and substantial redesigns move to a later cycle.

After hard freeze, only critical security vulnerabilities or release-blocking correctness or interoperability defects will be corrected. Corrections follow the [emergency procedure](#emergency-corrections) and require approval from more than half of all eligible Core Maintainers in a recorded vote.

## SEP review and inclusion

Sponsorship, submission, and finalization follow the [SEP workflow](/community/sep-guidelines#workflow). A working group lead or designated Core Maintainer submits proposals to the [SEP review queue](https://voting.modelcontextprotocol.io/p/seps). The queue accepts submissions year-round. Submitting a proposal does not guarantee review time or inclusion in a release.

### Review queue

Release managers maintain the review queue. Each entry records:

- A link to the proposal
- The sponsoring group and its representative
- The sponsor, if one is assigned
- Whether the request is for formal review or pre-review
- The readiness date, roadmap alignment, and target review cycle

An entry for formal review links to the SEP pull request in the specification repository. An entry for pre-review can link to an early proposal that does not yet have a SEP number or the sponsoring group's approval.

A working group lead or designated Core Maintainer can request a pre-review to discuss a proposal's direction, dependencies, and major concerns before the proposal is complete. A pre-review gives authors feedback but does not approve the proposal or reserve a place in a release.

### Review scheduling

Formal reviews take place at regular Core Maintainer meetings during the review window. Release managers build each meeting agenda from the queue in this order:

1. Proposals that are ready for formal review come before pre-reviews.
2. Within each of those two groups, roadmap-aligned proposals come first.
3. Among proposals with the same roadmap alignment, the proposal with the oldest readiness date comes first.

Release managers record the reason for any exception to this order in the queue. A proposal that is deferred only because the agenda was full keeps its readiness date. A proposal that was returned for substantive revision receives a new readiness date when it is resubmitted.

Each formal review follows the same steps:

1. Two weeks before the meeting, release managers select ready proposals with the Core Maintainers and publish the agenda and proposal links. They invite each proposal's authors and its working group lead or designated Core Maintainer to the meeting.
2. During the week before the meeting, reviewers leave comments on the pull request. Authors and sponsors respond and identify the questions that need discussion.
3. At the meeting, the author, working group lead, or designated Core Maintainer presents the proposal, the remaining questions, and any implementation feedback.
4. After the presentation, the sponsor opens the [acceptance vote](/community/sep-guidelines#review-and-acceptance), which remains open for seven calendar days.

### Inclusion in a release

A SEP reaches [Final status](/community/sep-guidelines#workflow) when its sponsor has verified all required artifacts, including the specification changes, reference implementation, and any required conformance tests. To be included in a release, a SEP must reach Final and have its pull request merged by the soft freeze date.

The release date does not move for unfinished proposals. SEPs that miss soft freeze are considered for later releases:

- Accepted SEPs keep their status unless a substantial redesign requires another review.
- Proposals awaiting a decision keep their status and return to the queue.

Inclusion in a later release depends on the proposal's readiness and that cycle's scope. Changes for future releases remain in proposal branches or pull requests until the current release is published.

The freeze rules in effect when a vote concludes apply to the change, even if the vote opened before the freeze. Approval does not exempt a change from the freeze rules in effect when it is merged.

The review window applies to all SEP types. Process and Informational SEPs take effect after acceptance and implementation, independently of specification publication. Extensions follow their [publication lifecycle](/extensions/overview#extension-lifecycle).

## SDK deadlines

SDK maintainers should begin implementation as soon as a SEP is accepted. They should report specification ambiguities to the author and sponsor while corrections can still be merged. SDK implementations are not required for a SEP to reach Final status.

[Tier 1 SDKs](/community/sdk-tiers) publish beta versions 1.5 months before the release and stable versions before the specification is published. The beta gives client and server developers half a month to report issues before hard freeze.

These deadlines cover the features required by the tiering policy, not experimental features or extensions. SDKs in other tiers are encouraged to publish betas on the same schedule.

Beta release notes identify the target specification release, the available functionality, known gaps, and where to report feedback. SDK maintainers work with release managers to keep the public readiness summary up to date with SDK versions, conformance results, gaps, owners, and expected resolution dates.

Release managers escalate a missed beta or stable milestone to the Core Maintainers and the [SDK Working Group](/community/working-groups/sdk) and report it in the release guidance. SDK delays do not postpone the specification release or automatically change an SDK's tier.

## Release managers

Each release has a primary and a secondary [release manager](/community/contributor-ladder#release-managers). The secondary becomes primary for the following release, and Core Maintainers select an incoming secondary before planning for that release begins.

The primary coordinates the release calendar, review scheduling, freezes, SDK readiness, and publication. The secondary works with the primary on the review queue and handoff notes while preparing to lead the next cycle.

During the two months when cycles overlap, the secondary also serves as primary for the following cycle and leads its planning with the incoming secondary. The outgoing primary remains accountable for the current release until it is published. On release day, the release managers complete the handoff notes with outstanding issues and their owners.

After the first release following this schedule, release managers publish a retrospective that covers queue wait times, readiness at soft freeze, SDK beta availability, emergency corrections, and release manager workload during the overlap.

The [maintainer roster](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md#release-managers) lists the current release managers. For the first release, two maintainers share the primary role.

## Emergency corrections

The primary release manager coordinates each correction after hard freeze through a regular pull request. A correction does not need a separate SEP, a sponsor, or a meeting presentation.

1. The primary confirms that the change meets the [hard-freeze criteria](#milestones). The pull request documents the defect, why the correction cannot wait for the next release, the smallest change that corrects the defect, and the effect on SDKs and release artifacts.
2. The primary opens a recorded vote of all eligible Core Maintainers. The vote can take place outside the review window. The primary can shorten the seven-day voting period, but must notify all eligible Core Maintainers of the deadline and the reason.
3. Maintainers of the affected implementations review the change, and the relevant regression and conformance checks are run. If the change alters observable protocol behavior, the conformance tests are updated.
4. After approval and validation, the pull request is merged. The primary records the vote, decision, and validation results, notifies the affected SDK maintainers, and updates the readiness summary and release notes.

If a defect cannot be corrected safely before the release, the affected feature and the changes that depend on it can be removed from the release. Removal follows the same procedure and vote. The rest of the specification is released on schedule.

Security-sensitive details follow the [security disclosure process](/community/policies#reporting-a-vulnerability). The decision and validation record stays in a restricted channel during an embargo and is published when disclosure permits.

## Transition to the new schedule

The first release following this schedule is targeted for March 30, 2027, which replaces the earlier December 2026 target. It uses the planning completed in August 2026, and its review window closes at the soft freeze date calculated from the March release date.

Planning for the September 2027 release begins in late January 2027, and planning for the March 2028 release begins in late July 2027.

SEP pull requests that were opened before the release cycle took effect remain valid. They keep their numbers, discussions, and completed decisions, and authors do not need to close and recreate them.

Before its next formal review, each of these proposals needs [sponsorship](/community/sep-guidelines#sponsors) from a working group or the Core Maintainer group and an entry in the review queue. Proposals that were already accepted remain accepted and must be Final and merged by the soft freeze date to be included in a release.
