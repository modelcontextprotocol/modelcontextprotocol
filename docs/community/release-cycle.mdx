MCP specification releases are published every six months, generally on the last Tuesday of March and September. [SEP-3398](/seps/3398) defines the release process.

## Schedule

Each release has an eight-month cycle, so planning for the next release starts two months before the current release is published. Release managers publish exact milestone dates and cutoff times at the start of planning. The intervals below are measured in calendar months.

Specification versions use the release date in [`YYYY-MM-DD` format](/docs/learn/versioning).

## Milestones

| Milestone                    | Before release | What happens                                                                                                      |
| ---------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------- |
| Planning begins              | 8 months       | Core Maintainers propose a roadmap and gather feedback from maintainers and working groups.                       |
| Core Maintainer review opens | 6 months       | Priorities are published and scheduled SEP reviews begin.                                                         |
| Soft freeze                  | 2.5 months     | Review closes. Every SEP included in the release must be Final and merged.                                        |
| Next-cycle planning begins   | 2 months       | Planning for the following release starts.                                                                        |
| SDK beta                     | 1.5 months     | Tier 1 SDKs publish betas supporting the frozen specification.                                                    |
| Hard freeze                  | 1 month        | Specification changes are restricted to emergency corrections.                                                    |
| Release                      | 0 months       | The specification, release notes, implementation and migration guidance, and SDK readiness summary are published. |

Between soft and hard freeze, changes are limited to bug fixes, polish, and clarifications within the frozen scope. After hard freeze, only critical security vulnerabilities or release-blocking correctness or interoperability defects may be corrected. Each such change requires approval through a full Core Maintainer vote.

## Getting a SEP into a release

Follow the [SEP workflow](/community/sep-guidelines#workflow) for sponsorship, submission, and finalization. A WG Lead or designated Core Maintainer submits the proposal to the [SEP review queue](https://voting.modelcontextprotocol.io/p/seps), which is open year-round. Roadmap-aligned proposals take priority; queue placement does not guarantee review time.

Release managers publish meeting agendas two weeks in advance. Allow time for the full seven-day [acceptance vote](/community/sep-guidelines#review-and-acceptance) and for completing the required artifacts: a release-bound SEP must be **Final and merged by soft freeze**, not merely accepted.

A SEP that misses soft freeze is considered for a later release. The release date does not change, and accepted SEPs keep their acceptance unless a substantial redesign requires renewed review. Changes for later releases stay in proposal branches or PRs until the current release is published.

All SEP types use the same review window. Process and Informational SEPs take effect once accepted and implemented, without waiting for a specification release. Extensions follow their own [publication lifecycle](/extensions/overview#extension-lifecycle).

## SDK deadlines

SDK maintainers should start implementation when a SEP is accepted and report ambiguities to its author and sponsor while corrections can still be merged. SDK implementations are not required for a SEP to reach Final.

[Tier 1 SDKs](/community/sdk-tiers) publish betas 1.5 months before release and stable support before specification publication. These deadlines cover the features required by the tiering policy, not experimental features or extensions.

SDK maintainers provide versions, conformance results, and outstanding blockers to release managers for the public readiness summary. Delays are disclosed in the release guidance; they do not postpone the specification release or automatically change an SDK's tier.

## Release managers

Each release has a primary and a secondary release manager, selected from self-nominated Maintainers by a majority of all eligible Core Maintainers. The secondary becomes primary for the following release, and Core Maintainers select an incoming secondary before that cycle's planning begins.

The primary is accountable for the calendar, review scheduling, freezes, SDK readiness, and publication. The secondary shares this work and prepares for the next cycle. Release managers coordinate the release; Core Maintainers decide SEP acceptance and hard-freeze exceptions.
