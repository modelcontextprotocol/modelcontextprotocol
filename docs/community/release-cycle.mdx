MCP specification releases are published every six months, generally on the last Tuesday of March and September.

## Schedule

Each release has an eight-month cycle. Planning for the next release starts two months before the current release is published. Release managers publish exact milestone dates and cutoff times at the start of planning. Milestone intervals are measured in calendar months.

Specification versions use the release date in [`YYYY-MM-DD` format](/docs/learn/versioning).

## Milestones

| Milestone                    | Before release | Outcome                                                                                                           |
| ---------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------- |
| Planning begins              | 8 months       | Core Maintainers propose a roadmap and gather feedback from maintainers and working groups.                       |
| Core Maintainer review opens | 6 months       | Priorities are published and scheduled SEP reviews begin.                                                         |
| Soft freeze                  | 2.5 months     | Review closes. Included SEPs must be [Final](/community/sep-guidelines#workflow) and merged.                      |
| Next-cycle planning begins   | 2 months       | Planning for the following release starts.                                                                        |
| SDK beta                     | 1.5 months     | Tier 1 SDKs publish betas supporting the frozen specification.                                                    |
| Hard freeze                  | 1 month        | Specification changes are restricted to emergency corrections.                                                    |
| Release                      | 0 months       | The specification, release notes, implementation and migration guidance, and SDK readiness summary are published. |

Between soft and hard freeze, changes are limited to bug fixes, polish, and clarifications within the frozen scope.

After hard freeze, only critical security vulnerabilities or release-blocking correctness or interoperability defects will be corrected. More than half of all eligible Core Maintainers must approve each correction in a recorded vote.

## SEP review and inclusion

Sponsorship, submission, and finalization follow the [SEP workflow](/community/sep-guidelines#workflow). A working group lead or designated Core Maintainer submits proposals to the [SEP review queue](https://voting.modelcontextprotocol.io/p/seps). The queue accepts submissions year-round, but roadmap-aligned proposals receive priority. Submitting a proposal does not guarantee review time.

Release managers publish meeting agendas two weeks before each meeting. The [acceptance vote](/community/sep-guidelines#review-and-acceptance) remains open for seven calendar days.

A SEP reaches [Final status](/community/sep-guidelines#workflow) when its sponsor has verified all required artifacts, including the specification changes, reference implementation, and any required conformance tests. Release-bound SEPs must reach this status and have their pull requests merged by the soft freeze date.

The release date is fixed and does not move for unfinished proposals. SEPs that miss the soft freeze date are considered for future releases, and accepted SEPs retain their status unless a substantial redesign requires another review. Changes for future releases remain in proposal branches or pull requests until the current release is published.

The review window applies to all SEP types. Process and Informational SEPs take effect after acceptance and implementation, independently of specification publication. Extensions follow their [publication lifecycle](/extensions/overview#extension-lifecycle).

## SDK deadlines

SDK maintainers should begin implementation upon SEP acceptance and report specification ambiguities to the author and sponsor while corrections can still be merged. SDK implementations are not required for a SEP to reach Final status.

[Tier 1 SDKs](/community/sdk-tiers) publish beta versions a month and a half before the release and stable versions before the specification is published. These deadlines cover the features required by the tiering policy, not experimental features or extensions.

SDK maintainers work with release managers to keep the public readiness summary up to date with SDK versions, conformance results, and outstanding blockers. SDK delays are reported in the release guidance, but they do not postpone the specification release or automatically change an SDK's tier.

## Release managers

Each release has a primary and a secondary [release manager](/community/contributor-ladder#release-managers). The secondary becomes primary for the following release, and Core Maintainers select an incoming secondary before planning for that release begins.

The primary coordinates the release calendar, review scheduling, freezes, SDK readiness, and publication. The secondary works with the primary on the review queue and handoff notes while preparing to lead the next cycle.

The [maintainer roster](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md#release-managers) lists the current release managers.
