MCP specification releases follow a fixed schedule. If you're writing a Specification Enhancement Proposal (SEP) or maintaining an SDK, this page shows when your work needs to be ready for the next release. The full process is defined in [SEP-3398](/seps/3398), and changing it requires a Process SEP.

## Schedule

Specification releases are published every six months, generally on the last Tuesday of March and September. Release versions use the `YYYY-MM-DD` format described in [Versioning](/docs/learn/versioning).

Each release has an eight-month cycle, so planning for the next release starts two months before the current release is published.

## Milestones

| Milestone                    | Timing                               | What happens                                                                                                                                                         |
| ---------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Planning begins              | Eight months before release          | Core Maintainers propose a roadmap and gather feedback from maintainers and working groups.                                                                          |
| Core Maintainer review opens | Six months before release            | Priorities are published and scheduled SEP reviews begin.                                                                                                            |
| Soft freeze                  | Two and a half months before release | Core Maintainer review closes. Every SEP in the release must be Final and merged. Until hard freeze, only fixes, polish, and clarifications within the frozen scope. |
| Next-cycle planning begins   | Two months before release            | Planning for the following release starts, overlapping this release's last two months.                                                                               |
| SDK beta                     | A month and a half before release    | Tier 1 SDKs publish betas that support the frozen specification.                                                                                                     |
| Hard freeze                  | One month before release             | Only fixes for critical security vulnerabilities and release-blocking correctness or interoperability defects, each approved by a full Core Maintainer vote.         |
| Release                      | Release day                          | The specification, release notes, implementation and migration guidance, and SDK readiness summary are published.                                                    |

<Note>
  The release date does not move for unfinished work. A SEP that misses soft
  freeze can go into a later release. If it was already accepted, it stays
  accepted. Only a substantial redesign sends it back for review.
</Note>

## Getting a SEP into a release

1. The author brings the idea to the working group that covers the area and gets the working group to agree to sponsor it. See [Before you write](/community/sep-guidelines#before-you-write) and [Sponsors](/community/sep-guidelines#sponsors).
2. The author opens the SEP pull request. If the author is not a member of the `modelcontextprotocol` GitHub organization, a WG Lead or the sponsor opens it. See [Workflow](/community/sep-guidelines#workflow).
3. A WG Lead submits the SEP to the [SEP review queue](https://voting.modelcontextprotocol.io/p/seps). The queue is open year-round. Roadmap-aligned SEPs are scheduled first, and a place in the queue does not guarantee review time.
4. Core Maintainers review queued SEPs at their meetings during the Core Maintainer review window, from six months before release until soft freeze. Release managers publish the agenda two weeks before each meeting. Acceptance requires a recorded seven-day vote in which more than half of all eligible Core Maintainers vote in favor.
5. Before soft freeze, the sponsor confirms that the specification text, schema changes, and changelog entry are in the pull request, the reference implementation is complete, and any required [conformance tests](/community/sep-guidelines#conformance-test-requirement) are merged. The sponsor then sets the SEP to Final, and the pull request is merged. Acceptance alone does not meet the cutoff.

Every SEP type goes through the Core Maintainer review window. Process and Informational SEPs take effect once accepted and implemented, without waiting for a release. Extensions Track SEPs are published under the [extension lifecycle](/extensions/overview#extension-lifecycle).

## SDKs

- SDK maintainers should start implementing a SEP once it is accepted and report ambiguities to the SEP author and sponsor right away. Clarifications can be merged until hard freeze.
- A month and a half before release, [Tier 1](/community/sdk-tiers) SDKs publish a beta that supports the frozen specification. They publish a stable release before the specification is published.
- Release managers track SDK versions, conformance results, and gaps in an SDK readiness summary, which is published with the release.
- A late SDK does not delay the specification release or, on its own, change the SDK's tier. The gap is disclosed in the release guidance.

## Release managers

Each specification release has a primary and a secondary release manager. Release managers are Maintainers who nominate themselves. Core Maintainers vote to select the secondary release manager before planning for that specification release begins. The secondary release manager becomes the primary release manager for the following specification release.

Release managers help run:

- The release calendar
- The SEP review queue and meeting agendas
- Freeze coordination
- SDK readiness tracking
- Publication

Core Maintainers decide which SEPs are accepted and which changes are allowed after hard freeze.
