This page describes the kinds of contribution the MCP project accepts, where each one happens, and the ground rules. MCP is developed in the open across the [`modelcontextprotocol`](https://github.com/modelcontextprotocol) GitHub organization: the specification, this documentation and Specification Enhancement Proposals (SEPs) live in [`modelcontextprotocol/modelcontextprotocol`](https://github.com/modelcontextprotocol/modelcontextprotocol), and each SDK and tool has its own repository. If you want to build with MCP rather than change it, see the [server](/docs/develop/build-server) and [client](/docs/develop/build-client) guides, the [SDK list](/docs/sdk) and the [MCP Registry](/registry/about).

## Join the work in progress

Protocol work is organized in [working groups and interest groups](/community/working-interest-groups). Their meetings are open to anyone and are listed on [meet.modelcontextprotocol.io](https://meet.modelcontextprotocol.io/). [Meetings and channels](/community/working-interest-groups#meetings-and-channels) sets out how a meeting is announced and minuted. No invitation or role is needed to attend or speak at a meeting, to comment on a pull request, or to open one. You do not need to belong to a group to open a pull request or submit a SEP. Every meeting runs under the [Antitrust Policy](/community/antitrust). Read it before attending, especially if you participate on behalf of an employer.

## Where to start

Issues labeled [`good first issue`](https://github.com/modelcontextprotocol/modelcontextprotocol/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22) and `help wanted` in the specification repository are sized for a first change. The SDK repositories use the [same label names](/community/sdk-tiers#issue-triage-labels). Documentation fixes and new schema examples under `schema/draft/examples/<TypeName>/` are also good starting points. [CONTRIBUTING.md](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/CONTRIBUTING.md#schema-examples) explains how to add an example.

Review, testing and triage count as much as code. Read and comment on open SEP and draft-specification pull requests, answer questions in GitHub Discussions, reproduce reported bugs, and test SDK release candidates against the draft specification. The [conformance suite](https://github.com/modelcontextprotocol/conformance) needs scenario authors: every Final Standards Track SEP with observable protocol behavior requires one (see [Conformance Test Requirement](/community/sep-guidelines#conformance-test-requirement)).

## Fix docs or spec text

Open a pull request against the specification repository. For a typo or a single paragraph the GitHub web editor is enough, and CI runs the checks. Clone the repository for larger edits and run `npm run prep` before pushing. Setup and troubleshooting are in [CONTRIBUTING.md](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/CONTRIBUTING.md).

`schema/draft/schema.ts` is the source of truth for the schema. Do not hand-edit the generated files `schema/draft/schema.json`, `docs/specification/draft/schema.mdx` and `docs/seps/*.mdx`. Released specification revisions are frozen, so fixes go to `draft/`. Keep each pull request to one concern. If a pull request with passing checks has had no response after a week, ping the requested reviewer in a comment, then ask in the group's or project's Discord channel.

## Work on an SDK or tool

Each SDK and each project (Inspector, Registry, the reference servers, the conformance suite, MCPB) has its own repository, maintainers (listed in [MAINTAINERS.md](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md)) and `CONTRIBUTING.md`, and that file governs contributions there. Processes differ between SDKs, some of which are co-maintained with other organizations. File bugs and pull requests in that repository: the specification repository does not take SDK bugs.

A bug fix that ships with a reproducing test is welcome as a direct pull request. For anything larger, open an issue in that repository first. The SDK list with each SDK's tier is at [/docs/sdk](/docs/sdk); the tier sets the triage and fix latency you can expect (see [SDK Tiers](/community/sdk-tiers)). Coordination happens in the SDK and project channels on [Discord](/community/communication#discord).

## Propose a protocol change

A change to the protocol itself goes through a SEP: a design document submitted as a pull request that adds a file to `seps/`. Bug fixes and clarifications to the specification text do not need one. [When you need a SEP](/community/sep-guidelines#when-you-need-a-sep) lists what does. A SEP needs a working prototype and a [sponsor](/community/sep-guidelines#sponsors), and Core Maintainers judge it against the [roadmap](/development/roadmap) and the [design principles](/community/design-principles).

Raise the idea in the working or interest group that covers the area first. Many ideas should ship as an [extension](/extensions/overview) before they become core protocol. The full procedure is in [SEP Guidelines](/community/sep-guidelines).

## Where to talk

[Discord](/community/communication#discord) is for contributors working on the protocol and its projects, not for user support. [GitHub Discussions](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions) is for ideas, questions and announcements. Actionable bugs and scoped tasks go in [GitHub Issues](https://github.com/modelcontextprotocol/modelcontextprotocol/issues), filed through the issue forms; SEPs are pull requests, not issues. Never report a vulnerability in public: see [Reporting a vulnerability](/community/policies#reporting-a-vulnerability). [Communication](/community/communication) lists the channel names, the rules for private channels, and where decisions are recorded.

## Growing your role

Sustained contributors are sponsored to Member and then to Maintainer, and in practice you become maintainer of something specific: an SDK, a tool, a documentation area or a group. The [Contributor Ladder](/community/contributor-ladder) defines each role and how to be nominated, [Governance](/community/governance) defines who decides what, and [MAINTAINERS.md](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md) lists the current maintainers.

## Ground rules

The [Code of Conduct](/community/policies#code-of-conduct) applies in every repository, channel and meeting. Any AI assistance used for a contribution must be [disclosed](/community/policies#ai-assisted-contributions) in the pull request or issue. Contributions are licensed under Apache-2.0 for code and specifications and CC-BY-4.0 for other documentation (see [Project Policies](/community/policies#licensing-and-intellectual-property)).
