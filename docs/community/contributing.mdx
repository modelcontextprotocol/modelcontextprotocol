---
title: Contributing to MCP
description: How to contribute to the Model Context Protocol specification, docs and SDKs.
---

MCP is an open source project that welcomes contributions from the community. You don't need a change ready to get involved.

You'll find the specification, these docs and Specification Enhancement Proposals (SEPs) in the [specification repository](https://github.com/modelcontextprotocol/modelcontextprotocol). Each SDK and tool has its own repository in the [`modelcontextprotocol`](https://github.com/modelcontextprotocol) organization.

To build with MCP, start with the [server](/docs/develop/build-server) and [client](/docs/develop/build-client) guides, the [SDK list](/docs/sdk) or the [MCP Registry](/registry/about).

## Where to start

<Steps>
<Step title="Join Discord">

Contributors talk about the protocol on [Discord](/community/communication#discord).

</Step>
<Step title="Find your group">

Pick the [working group](/community/working-interest-groups#current-groups) or Discord channel that covers your area. If none fits, use `#general`.

</Step>
<Step title="Talk to the lead">

Each group's page names its leads. Post what you want to work on in the group's channel.

</Step>
</Steps>

Anyone can join a group meeting, comment on a pull request or open an issue. Check the [calendar](https://meet.modelcontextprotocol.io/) and read the [Antitrust Policy](/community/antitrust) before you attend.

## Report a problem

[Report a vulnerability](/community/policies#reporting-a-vulnerability) in private.

For a bug, typo or unclear text in the specification or these docs, open an [issue](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/new/choose). For an SDK or tool, open it in that repository.

Please don't post usage questions in the repositories. We stopped taking them there because of spam.

## Change the specification or docs

You need write access to open a pull request on the specification repository. If you don't have it, a maintainer can open one for you.

<Steps>
<Step title="Raise the change">

Report a bug in an issue. Raise anything else in your group's channel or `#general`.

</Step>
<Step title="Push a branch">

Push to a fork, or to a working group repository you can write to. Specification fixes go in `draft/`. Keep each change to one concern. [CONTRIBUTING.md](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/CONTRIBUTING.md) covers setup and checks.

</Step>
<Step title="Ask for a pull request">

Link the branch in that issue or channel and ask a maintainer to open a pull request that credits you.

</Step>
</Steps>

A change to the protocol itself needs a [SEP](#propose-a-protocol-change).

## Work on an SDK or tool

Inspector and the reference servers accept issues only.

<Steps>
<Step title="Read the contributing guide">

Each repository sets its own rules, and some close pull requests that have no assigned issue. If a repository has no guide, ask in its channel, such as `#python-sdk-dev`.

</Step>
<Step title="Pick an issue">

Look for [`good first issue`](https://github.com/search?q=org%3Amodelcontextprotocol+is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22&type=issues) or `help wanted`, or open a new one. Ask to be assigned if the guide requires it.

</Step>
<Step title="Open a pull request">

For anything larger than a small bug fix, agree on the approach in the issue before you write code.

</Step>
</Steps>

The [SDK list](/docs/sdk) shows each SDK's [tier](/community/sdk-tiers), which sets its issue triage times.

## Propose a protocol change

Protocol changes go through a [SEP](/community/sep-guidelines). Bug fixes and clarifications [do not need one](/community/sep-guidelines#when-you-need-a-sep).

<Steps>
<Step title="Discuss the idea">

Raise it in your group's channel. The SEP pull request [must link to that discussion](/community/sep-guidelines#before-you-write).

</Step>
<Step title="Build a prototype">

See [Prototype Requirements](/community/sep-guidelines#prototype-requirements). Consider shipping the idea as an [extension](/extensions/overview) where its shape allows.

</Step>
<Step title="Find a sponsor">

See [Sponsors](/community/sep-guidelines#sponsors).

</Step>
<Step title="Write the SEP">

Follow the [workflow](/community/sep-guidelines#workflow). Without write access, ask your sponsor to open the pull request.

</Step>
</Steps>

## Other ways to help

- Review open SEPs and draft specification pull requests.
- Reproduce reported bugs.
- Test SDK release candidates against the draft specification.
- Write [conformance](https://github.com/modelcontextprotocol/conformance) scenarios. A Standards Track SEP with observable protocol behavior [needs one](/community/sep-guidelines#conformance-test-requirement) to reach Final.

## Growing your role

To take on a bigger role, see the [Contributor Ladder](/community/contributor-ladder). [Governance](/community/governance) covers who decides what, and [MAINTAINERS.md](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md) lists the current maintainers.

## Ground rules

- The [Code of Conduct](/community/policies#code-of-conduct) applies in every repository, channel and meeting.
- [Disclose](/community/policies#ai-assisted-contributions) any AI assistance in the pull request or issue.
- AI agents must follow [AGENTS.md](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/AGENTS.md), which limits when they can open issues and pull requests.
- Contributions are [licensed](/community/policies#licensing-and-intellectual-property) under Apache-2.0 for code and specifications and CC-BY-4.0 for other documentation.
