This page sets out the project's communication channels, when a channel may be private, and where decisions are recorded. It was adopted by [SEP-994](/seps/994-shared-communication-practicesguidelines), a Specification Enhancement Proposal (SEP), and is changed by a Process SEP. The [Code of Conduct](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/CODE_OF_CONDUCT.md) governs every channel. If you are new to the project, start at [Contributing](/community/contributing).

## Channels

| Channel                                                                                        | Use it for                                                                                                                                                                         |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Discord](https://discord.gg/6CSzBmMkjX)                                                       | Real-time coordination among contributors, including working group, interest group and SDK discussion                                                                              |
| [Meeting calendar](https://meet.modelcontextprotocol.io/)                                      | Open group and maintainer meetings. For how meetings run, see [Meetings and channels](/community/working-interest-groups#meetings-and-channels)                                    |
| [GitHub Discussions](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions) | Ideas, feature requests with rationale, questions, roadmap discussion, announcements and releases, and meeting agendas and notes (Meeting Notes category)                          |
| [GitHub Issues](https://github.com/modelcontextprotocol/modelcontextprotocol/issues)           | Reproducible bugs, scoped documentation tasks, and CI and release tasks, filed through the issue forms. [SEPs](/community/sep-guidelines) are pull requests to `seps/`, not issues |
| [Security advisories](/community/policies#reporting-a-vulnerability)                           | Vulnerabilities. Never post one in a public channel                                                                                                                                |

Each SDK and project repository has its own issue tracker and Discord channel. A repository without Discussions enabled uses Issues instead. Vulnerability reports follow the [Security Policy](/community/policies#reporting-a-vulnerability).

## Discord

The [MCP Contributor Discord](https://discord.gg/6CSzBmMkjX) is for people working on the protocol and its projects. It is not a support channel: MCP users should read the documentation and ask in GitHub Discussions. Do not market products or services on the server, and mention vendors only as examples relevant to the specification.

Channels are named `#general` for project-wide discussion, `#<name>-wg` and `#<name>-ig` for each working group and interest group, and `#<lang>-sdk-dev` for each SDK. Other projects have a channel such as `#inspector-dev`. Propose a new group in `#wg-ig-group-creation`. Responses are best-effort.

Channels are public by default. Private channels are restricted to designated maintainers and Community Moderators and exist only for security incidents (CVEs and protocol vulnerabilities), people and Code of Conduct matters, and coordination that needs an immediate or focused response from a limited audience. Some maintainer decision channels are read-only. A private channel is a temporary incident room, not a place for routine development. Matters concerning an individual contributor may remain private.

## Decision records

Discord is not the record. A Discord discussion heading toward a technical or governance decision must move to a GitHub Discussion or Issue. Every technical or governance decision, including a Core Maintainer outcome on a SEP, is written up in a Discussion or Issue with the `notes` label, or on the SEP's pull request. Specification changes are also recorded in the [changelog](/specification/draft/changelog), and process changes in these community pages.

A record names who decided, the context, the options considered, the rationale, and the next steps. For meeting agendas and notes, see [Meetings and channels](/community/working-interest-groups#meetings-and-channels).
